# Ditto 랜딩 최종안 — 앱 디자인 시스템·동작 대조

검토일: 2026-11-12. 실제 앱 소스와 최신 정책을 우선하며, 오래된 기획 문서와 다른 부분은 구분한다. 이 검토에서는 앱·서버를 수정하거나 실제 발급을 실행하지 않았다.

배지 상태는 available / collected / unavailable. collected는 표시만 하고 또 누르거나 길게 누르게 하지 않는다. 사본 카드의 배지는 **우상단**이고 출처는 좌하단이다(`DittoWidgetTile.swift:5`). 원본의 허용 배지와 사본의 수집 배지는 문맥을 구분한다.

## 4. 주파수: 연출과 실제 정책 구분

최신 구현 근거는 `AppState.swift:387` 및 `:450`, 최신 정책은 `docs/policy/FREQUENCY_POLICY.md`. `docs/specs/Ditto_주파수_정책서.md`에는 예전 28일·21일 숙성 문구가 남아 있으므로 그대로 사용하지 않는다.

- 네 시각 단계: 잔잔 **#8E919E** → 선명 **#2BC4A8** → 곧 열림 **#5A5BF2** → 열림 **#AA4AF4**, 끝 핑크 **#FA97E2**. 밝은 바탕의 작은 글은 각각 #6E7280 / #138A76 / #4446D0 / #862FC6.
- 서버 stage는 calm·clear·open 세 가지이며 곧 열림은 clear 내부 nearOpen 판정이다.
- 주파수는 최근 **21일 동안의 교류를 살피는 창**이지 21일이 지나면 자동으로 친구가 되는 타이머가 아니다. 랜딩의 날짜 타임라인은 **한 관계의 예시**라고 표시한다.
- 현재 앱 코드의 게이트는 점수 10, 교류 3일, 함께한 교류를 본다. 실제 사용자 화면에는 점수나 달성률을 표시하지 않는다. 기존 랜딩 FAQ의 **4일**은 구버전이므로 '여러 날에 걸쳐 주고받은 교류'로 정리한다.
- 열림 → 애칭·편지와 함께 **친구 신청** → 상대 **수락** → 친구. 열림과 친구 완료를 같은 사건으로 만들지 않는다. ASCII 두 신호가 마크로 합쳐지는 마지막 연출에는 신청·수락을 명시한다.
- 앱의 실제 그래픽은 **17열×9행 점 매트릭스**, 5개 피크, 화면 밖에서 정지, Reduce Motion 시 정지. ASCII 대형 장면은 랜딩용 해석이며 앱 캡처라고 표기하지 않는다.
- 실제 신호: 디토, 함께 단 댓글, 리액션, 방문, 같은 그룹 대화, 만남. 상호 교류가 없는 일방 방문만으로 친구 신청이 열리는 설명은 피한다.
- 친구가 되면 라이브 주파수 대상에서 빠지고 친구 탭으로 이동한다. 관계 지도에서 친구 30명 목표를 제시하는 방식은 앱 친구 한도 15명과 충돌하므로 '6개월 동안 이어진 관계'처럼 친구·친구의 친구 합계로 구분한다.

## 5. 카메라와 초대장 발급의 실제 경계

- 색감 카메라 라이브러리와 같이 찍기는 `CameraLooks.swift:68`의 **Debug/TestFlight** 게이트다. 공개 App Store 기능과 동일하다고 단정하지 않는다. 페이지에서는 '앱에서 준비 중인 색감을 먼저 체험해요' 같은 문구로 현재 공개 범위를 정확히 알릴 수 있다.
- 카메라 사진은 브라우저 캔버스에서 처리하고 초대장 이미지에 합성할 수 있다. 이름·아이디를 넣은 **기념 카드 미리보기와 이미지 저장**은 서버 변경 없이 가능하다.
- 현재 랜딩 `index.html:4346–4353`: 이메일 정규식과 동의 체크를 통과한 뒤 `claim_launch_ticket`에 `p_nickname`, `p_name`, **`p_email`**, **`p_consent:true`** 등을 보낸다. 성공 응답의 `row.no`, `row.code`를 카드에 인쇄한다. 유효한 초대 코드는 이 서버 응답을 써야 한다.
- `HOME_V8_SPEC.md`도 서버가 이메일당 한 장이라고 명시한다. 해당 RPC SQL 정의는 이번 로컬 소스 검색에서 찾지 못했으므로 서버 제약 자체를 별도로 변경·검증했다고 주장하지 않는다.
- 따라서 서버 변경 없이 **이름·아이디만으로 유효한 코드를 발급했다**고 할 수 없다. 권장 구현은 `사진→이름·아이디→초대장 미리보기·이미지 저장→실제 코드 받기(이메일·동의)→코드 복사·발급 카드 저장`이다. 로컬 랜덤 문자열이나 가짜 이메일로 발급을 대신하지 않는다.
- 사용자가 이름·아이디만으로 **실제 코드 발급**을 반드시 원한다면 별도 RPC·중복발급 정책·스팸 방지·개인정보 계약 변경이 필요하다. 이번 웹 디자인에서는 기존 안전한 서버 계약을 이어 쓸 수 있다.

## 6. 구현 체크리스트

1. 실제 앱 토큰을 CSS 변수로 매핑하고 위젯 렌더러에서 기존 `.dw` 선택자 충돌을 차단한다.
2. 3열 피드→8칸 플래터 전환에서 같은 콘텐츠 필드가 이동하여 자유 배치를 이해시키고, 키보드용 배치·크기 버튼을 함께 제공한다.
3. 사진 슬롯을 비워도 이미지의 제목·출처·배지·크기·방향은 보여 준다. 더미 인물/사진 요청을 넣지 않는다.
4. 디토 원작자·공유자·수집자를 구분하고, 취소·중복·3개 꽉 참·비친구 잠금도 설명한다.
5. 주파수는 예시 시간표이며 신청과 수락 후에만 친구 심볼을 완성한다.
6. 카메라 권한 거절·파일 대안·찍기·재촬영·섹션 이탈 중지·저장 실패 상태를 확인한다.
7. 실제 발급은 서버 응답 코드만 사용하고, 검증 과정에서는 서버 쓰기를 차단한다.
